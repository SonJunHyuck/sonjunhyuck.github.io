# 포트폴리오·개발 블로그 8단계 운영 방식

이 문서는 새 프로젝트와 개발 글을 꾸준히 추가하면서 품질과 배포 안정성을 지키기 위한 기본 절차입니다. 작은 오탈자 수정도 가능한 한 이 흐름을 따르되, 긴급 복구는 배포 후 기록을 남깁니다.

## 1. 수집과 우선순위 결정

아이디어, 완료한 작업, 독자가 자주 묻는 질문을 이슈 또는 백로그에 기록합니다. 각 항목에는 독자, 핵심 질문, 기대 결과, 공개 가능 여부를 적습니다. 포트폴리오는 공개 가능한 수치·이미지·고객명을 먼저 확인합니다.

## 2. 발행 기획

글 또는 프로젝트의 제목, 한 줄 요약, URL 슬러그, 분류, 핵심 키워드, 공개 목표일을 정합니다. 중복 주제와 기존 글의 내부 링크 기회를 확인합니다. 프로젝트 글은 문제 → 기여 → 구현 → 결과 → 회고 순서를 기본 구조로 사용합니다.

## 3. 초안과 자료 준비

Astro 콘텐츠 컬렉션의 정해진 위치에 Markdown 또는 MDX로 작성합니다. 발행일, 제목, 설명, 태그, 초안 여부, 대표 이미지는 콘텐츠 스키마에 맞춰 채웁니다. 이미지에는 의미 있는 대체 텍스트를 쓰고, 외부 자료·코드·수치는 출처와 사용 권한을 기록합니다.

## 4. 구현과 로컬 확인

화면·컴포넌트 변경은 콘텐츠와 함께 작업 브랜치에서 구현합니다. 로컬 개발 서버에서 데스크톱과 모바일 폭을 확인하고, Astro의 실제 빌드 명령으로 정적 생성 오류를 점검합니다. 깨진 내부 링크, 이미지 경로, 코드 블록, 날짜·태그 표기를 확인합니다.

## 5. 편집·접근성 검수

제목과 요약만 읽어도 글의 가치가 전달되는지, 첫 문단이 독자의 문제와 맞는지 확인합니다. 맞춤법, 용어, 코드 실행 가능성, 링크 대상과 발행일을 검수합니다. 제목 계층, 대체 텍스트, 색 대비, 키보드 탐색, 모바일 가독성을 함께 확인합니다.

## 6. Pull Request 검토

작업 목적, 화면 영향, 검증 결과를 Pull Request에 적습니다. 작성자 외 한 사람이 콘텐츠 정확성 또는 UI 품질을 검토하는 것을 권장합니다. 검토자는 불필요한 개인정보·비공개 정보, 저작권 문제, 깨진 링크, 검색용 설명 누락을 확인합니다.

## 7. 병합과 GitHub Pages 배포

필수 검토와 빌드가 통과한 변경만 기본 브랜치에 병합합니다. GitHub Actions의 배포 실행 결과가 성공인지 확인하고, 실패하면 로그·재현 방법·영향 범위를 이슈에 남깁니다. Pages의 배포 원본과 사용자 지정 도메인 설정은 변경 권한을 가진 사람이 관리합니다.

## 8. 배포 후 확인과 개선

실제 공개 URL에서 새 페이지, 홈·목록 노출, 대표 이미지, 내부·외부 링크, 모바일 화면을 확인합니다. 오류가 있으면 즉시 수정하거나 필요한 경우 이전 정상 변경으로 되돌립니다. 발행 후 반응, 검색 유입, 오래된 기술 정보와 링크를 정기적으로 검토해 업데이트 작업으로 전환합니다.

## 권장 리듬

- 매 발행: `docs/CHECKLIST.md`의 작성·검수·배포 항목 완료
- 매월: 오래된 링크, 의존성, 페이지 성능, 미완성 초안 확인
- 분기별: 소개 문구, 대표 프로젝트, 기술 스택, 분석 지표와 백업·도메인 설정 점검

## 역할 원칙

콘텐츠 작성자는 사실성과 출처를 책임지고, 변경 작성자는 빌드와 화면 확인을 책임지며, 병합 담당자는 배포 상태를 확인합니다. 한 사람이 모든 역할을 맡더라도 각 확인 항목을 생략하지 않습니다.
