# 포트폴리오·개발 블로그 8단계 운영 방식

이 문서는 새 콘텐츠 발행과 배포 작업의 참고 절차입니다. 현재 작업에 해당하는 단계만 읽고 수행합니다. 국소 수정과 검증 생략·범위는 [AGENTS.md](../AGENTS.md)를 따르며, 이 문서가 별도의 검증·리뷰·배포를 요구하지는 않습니다. 개발 글은 공개 Notion DevLog에서 관리합니다.

## 1. 수집과 우선순위 결정

아이디어, 완료한 작업, 독자가 자주 묻는 질문을 이슈 또는 백로그에 기록합니다. 각 항목에는 독자, 핵심 질문, 기대 결과, 공개 가능 여부를 적습니다. 포트폴리오는 공개 가능한 수치·이미지·고객명을 먼저 확인합니다.

## 2. 발행 기획

글 또는 프로젝트의 제목, 한 줄 요약, URL 슬러그, 분류, 핵심 키워드, 공개 목표일을 정합니다. 중복 주제와 기존 글의 내부 링크 기회를 확인합니다. 프로젝트 글은 문제 → 기여 → 구현 → 결과 → 회고 순서를 기본 구조로 사용합니다.

## 3. 초안과 자료 준비

프로젝트는 Astro 콘텐츠 컬렉션에 Markdown으로, 개발 글은 Notion DevLog에 작성합니다. 발행일, 제목, 설명, 태그, 초안 여부, 대표 이미지는 콘텐츠 스키마에 맞춰 채웁니다. 이미지에는 의미 있는 대체 텍스트를 쓰고, 외부 자료·코드·수치는 출처와 사용 권한을 기록합니다.

## 4. 구현과 로컬 확인

화면·컴포넌트 변경은 콘텐츠와 함께 구현합니다. 빌드·화면 확인의 필요 여부와 범위는 AGENTS.md에 따르며, 필요한 검증은 변경을 모아 한 번 수행합니다.

## 5. 편집·접근성 검수

새 콘텐츠는 제목·요약·본문의 일관성과 사실 근거를 확인합니다. 접근성·링크·이미지 검증은 변경 영향이 있는 항목만 선택합니다.

## 6. Pull Request 검토

작업 목적, 화면 영향, 검증 결과를 Pull Request에 적습니다. 별도 검토자 필요 여부는 AGENTS.md의 작업 규모·영향 기준으로 판단합니다. 검토자는 불필요한 개인정보·비공개 정보, 저작권 문제, 깨진 링크, 검색용 설명 누락을 확인합니다.

## 7. 병합과 GitHub Pages 배포

사용자가 승인한 작업 범위 안에서 필요한 검증과 저장소의 필수 검사를 통과한 변경을 기본 브랜치에 병합합니다. GitHub Actions의 배포 실행 결과가 성공인지 확인하고, 실패하면 로그·재현 방법·영향 범위를 이슈에 남깁니다. Pages의 배포 원본과 사용자 지정 도메인 설정은 변경 권한을 가진 사람이 관리합니다.

## 8. 배포 후 확인과 개선

실제 배포를 수행한 경우 배포 성공과 변경된 공개 경로의 반영 여부를 확인합니다. 로컬에서 통과한 화면 검증은 배포 환경 차이나 오류 징후가 있을 때만 반복합니다. 오류가 있으면 즉시 수정하거나 필요한 경우 이전 정상 변경으로 되돌립니다. 발행 후 반응, 검색 유입, 오래된 기술 정보와 링크를 정기적으로 검토해 업데이트 작업으로 전환합니다.

## 권장 리듬

- 매 발행: `docs/CHECKLIST.md`의 해당 항목만 적용
- 매월: 오래된 링크, 의존성, 페이지 성능, 미완성 초안 확인
- 분기별: 소개 문구, 프로젝트 구성, 기술 스택, 분석 지표와 백업·도메인 설정 점검

## 역할 원칙

콘텐츠 작성자는 사실성과 출처를 책임지고, 변경 작성자는 빌드와 화면 확인을 책임지며, 병합 담당자는 배포 상태를 확인합니다. 한 사람이 역할을 겸할 수 있으며, 검증 범위와 생략 기준은 AGENTS.md를 따릅니다.
