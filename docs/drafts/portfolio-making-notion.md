## 제작 배경과 도구 선택

면접관이 별도의 파일을 내려받지 않고도 이력과 프로젝트를 확인할 수 있도록 웹 포트폴리오를 제작했습니다. 기존 프로젝트의 구현 내용과 제 기여를 정리해, 하나의 링크로 소개하는 것이 목적이었습니다.

포트폴리오는 콘텐츠를 보여주는 것이 중심이므로, 별도의 백엔드 없이 정적 사이트를 배포할 수 있는 GitHub Pages를 선택했습니다. 제작 도구는 Jekyll 등을 후보로 두고 AI와 장단점을 비교한 뒤, 이 프로젝트에 적합하다고 판단한 Astro를 선택했습니다.

동시에 **웹 프런트엔드 경험이 부족한 상황에서, AI를 활용하면 구현 세부사항에 얼마나 덜 관여하면서 원하는 결과를 만들 수 있는지** 탐구하고자 했습니다.



## 개별 수정에서 공통 규칙으로

초기에는 화면과 문구를 보며 필요한 수정을 요청했습니다. 사이트의 틀이 잡히고 프로젝트 상세 페이지가 늘어나자, 페이지마다 제목과 본문의 간격, 카드 구성, 강조 방식 등이 서로 달라지는 문제가 드러났습니다.

이를 제어하기 위해 **반복해서 적용할 판단을 공통 규칙으로 정리**했습니다. 공통 작업 원칙은 `AGENTS.md`, 분야별 적용 기준은 `SKILL.md`, 상세 절차와 예외는 매뉴얼에 기록했습니다. 프로젝트별 설명은 달라도 같은 기준으로 읽히도록 구성하고자 했습니다.

> 공통 작업 원칙은 AGENTS.md, 분야별 적용 조건과 참고 안내는 SKILL.md, 상세 절차·예시·예외는 매뉴얼을 단일 원본으로 관리한다.

## 검증의 목적과 담당을 구분하기

규칙을 도입하면서 페이지의 일관성은 나아졌지만, 작업 중 토큰 사용량이 크게 늘어나는 구간이 생겼습니다. 처음에는 참조해야 할 문서가 늘어난 영향도 의심했지만, 작업 과정을 살펴보며 높은 추론 강도의 모델이 불필요한 범위까지 검증하고 있다는 점을 확인했습니다.

처음에는 추론과 검증을 높은 추론 강도의 모델에, 구현을 낮은 추론 강도의 모델에 맡기도록 역할을 나눴습니다. 하지만 제가 기대한 검증은 **내용과 결과가 요청의 의도에 맞는지 판단하는 것**이었고, 실제로는 빌드나 버튼의 모양을 확인하는 기술적 검사까지 같은 역할에 포함되고 있었습니다.

이를 계기로 **의도와 합의에 대한 판단, 구현 결과의 기술적 확인을 구분**했습니다. 구현 담당 모델이 변경에 필요한 빌드와 화면 확인을 수행하고, 그 결과를 바탕으로 요청의 취지에 맞는지 판단하도록 정책을 수정했습니다. 단순 문구 수정은 변경 차이만 확인하는 등 검증 범위도 작업의 영향에 맞춰 정했습니다.

## 재시도에도 중단 기준 두기

이후에도 특정 작업에서 예상보다 많은 토큰이 사용됐습니다. 화면 검증이 실패했을 때 추가 시도가 반복되면서 작업 범위가 커지는 경우였습니다.

이를 줄이기 위해 **화면 검증에 실패하면 멈추고, 실패 이유와 함께 재시도 여부를 확인하도록** 기준을 세웠습니다. 이미 확보한 검증 결과는 재사용하고, 문서와 도구 출력도 현재 판단에 필요한 부분만 확인하도록 정리했습니다.

- 문구·오탈자·지침 수정: 변경 차이 확인
- 배치·스타일·동작 변경: 변경된 구간과 관련 조건 검증
- 이미 통과한 검증: 새 변경이나 오류 근거가 없으면 결과 재사용
- 화면 검증 실패: 추가 시도를 멈추고 재시도 여부 확인
- 파일·로그·화면 정보 조회: 필요한 구간과 속성만 확인

> 의미를 유지한 문구·오탈자·띄어쓰기 수정과 지침·매뉴얼 편집은 변경 차이만 확인한다.
> 화면 검증이 실패하면 추가 시도를 멈추고 실패 이유를 간단히 알린 뒤 사용자에게 재시도 여부를 묻는다.

## 마치며

이 프로젝트는 기존 작업을 소개하는 웹사이트를 만드는 동시에, AI에 구현을 맡기고 결과를 검토하는 방식을 탐구한 과정입니다. 구현 세부사항에 직접 관여하는 부담은 줄일 수 있었지만, 원하는 결과의 기준을 정하고 작업이 그 방향으로 진행되는지 판단하는 역할은 계속 필요했습니다.

현재도 사이트를 수정하며 드러나는 문제를 작업 기준에 반영하고 있습니다. **AI가 수행할 범위와 사람이 판단할 지점을 구체화하면서**, 원하는 결과를 더 일관되게 얻는 방향으로 활용 방식을 다듬고 있습니다.
